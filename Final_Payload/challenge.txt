[1. OVERVIEW]
--------------------------------------------------------------------------------
Congratulations on reaching the final challenge!

Up until now, every exercise held your hand: the vulnerabilities were isolated, 
the functions were named `vulnerable()` or `win()`, and hints pointed directly 
to the bug.

In real security research and competitive CTFs, binaries do not announce their 
vulnerabilities. You are handed a compiled binary, perhaps standard libraries, 
and a remote network port. There is no source code.

This challenge presents a realistic, small command-line application (such as a 
"Secure Notes" service or task manager). Your mission is to conduct complete 
black-box analysis, identify the vulnerability, craft a reliable exploit locally, 
and fire it against the remote server to claim the flag.


[2. CHALLENGE DESCRIPTION]
--------------------------------------------------------------------------------
"A secure service has been deployed. Can you find the flaw, break through the 
 defenses, and capture the flag?"

You are provided with:
  • `chall`                : The compiled 64-bit ELF binary (stripped or unstripped)
  • `libc.so.6`            : The exact glibc shared library running on the server
  • `ld-linux-x86-64.so.2` : The dynamic linker used by the remote environment
  • Remote endpoint        : Host and port (e.g. nc localhost 1337)
  • NO SOURCE CODE!


[3. THE PROFESSIONAL PWN WORKFLOW]
--------------------------------------------------------------------------------
Follow this standard methodology used by CTF players and vulnerability researchers:

       [1. FILE RECON]
       $ file chall
       Determine architecture (x86-64), linking (dynamic/static), and symbol status.
              ↓
       [2. CHECKSEC]
       $ checksec --file=chall
       Check Canary, NX, PIE, and RELRO.
              ↓
       [3. STRINGS & STRACE]
       $ strings -n 6 chall
       Find interesting hardcoded strings, prompts, menus, and hidden easter eggs.
              ↓
       [4. REVERSE ENGINEERING (GHIDRA / IDA / GDB)]
       Decompile functions and analyze the control flow:
       - Which menu options exist?
       - Where is user input stored?
       - Are inputs bounded by `fgets`/`read` or unbounded like `gets`/`scanf("%s")`?
       - Is there an integer overflow, off-by-one, or format string vulnerability?
              ↓
       [5. VULNERABILITY & OFFSET DISCOVERY]
       Trigger the crash in GDB, generate patterns (`cyclic 200`), and calculate 
       the precise offset to saved RIP.
              ↓
       [6. ENVIRONMENT MATCHING (PWNINIT / PATCHELF)]
       Ensure your local binary uses the exact provided `libc` and `ld`:
       $ pwninit   (or patchelf --set-interpreter ... --set-rpath ...)
              ↓
       [7. EXPLOIT DEVELOPMENT]
       Chain the techniques:
       Stage 1: Leak a libc address (e.g. via puts(puts@GOT) or program leak)
       Stage 2: Loop back to `main()` to keep the program alive
       Stage 3: Calculate libc base and prepare `system("/bin/sh")` ROP payload
       Stage 4: Trigger the overflow a second time to execute the shell!
              ↓
       [8. REMOTE TESTING & FLAG EXTRACTION]
       Switch pwntools target from `process()` to `remote(HOST, PORT)`:
       $ cat /home/ctf/flag.txt
       FLAG!

[5. PROGRESSIVE HINTS]
--------------------------------------------------------------------------------
Hint 1: Start with reconnaissance. Run `checksec --file=chall`. What protections 
        are enabled? Knowing what is ON and what is OFF dictates your entire attack 
        vector.

Hint 2: Open the binary in a decompiler (Ghidra or IDA) or disassemble with GDB. 
        Trace every user input function. Does the size read ever exceed the 
        destination buffer size?

Hint 3: To ensure your local exploit matches remote behavior, use `pwninit` or 
        `patchelf` to bind the provided `libc.so.6` and `ld-linux-x86-64.so.2` 
        to the binary.

Hint 4: If you need to leak libc and execute a shell in one run, remember that 
        returning to `main` or the vulnerable function's start at the end of 
        your first ROP payload gives you a clean second chance to send your final 
        `system('/bin/sh')` payload!
