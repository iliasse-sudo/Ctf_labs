[1. OVERVIEW]
--------------------------------------------------------------------------------
In the previous challenges, memory addresses were static and predictable. You 
could inspect the binary once in GDB, hardcode `0x401156` into your script, and 
run it 100 times with identical success.

In real-world modern systems, this luxury does not exist. 

Operating systems use ASLR (Address Space Layout Randomization). Every time a 
program is launched, the operating system randomly shifts where libraries, the 
stack, the heap, and (with PIE) the binary itself are loaded in virtual memory.

Hardcoding addresses in an ASLR-enabled environment will cause your exploit to 
crash 99.999% of the time. To defeat ASLR, you need an "Information Leak".


[2. CHALLENGE DESCRIPTION]
--------------------------------------------------------------------------------
"The address changes every time you run the program. Why? Can you illuminate 
 the blind spot and find where things really live?"

The binary contains a function that leaks an internal pointer:
    void leak(void)
    {
        printf("Here is something interesting: %p\n", some_function);
    }

Your goal:
  1. Understand why addresses change across different executions.
  2. Parse the leaked runtime address.
  3. Calculate the randomized base address of the module.
  4. Deduce the exact runtime location of other functions.


[3. UNDERSTANDING ASLR & MEMORY PAGES]
--------------------------------------------------------------------------------
ASLR randomizes the base address of a module, but it does NOT randomize code 
inside the module byte-by-byte. 

Libraries and executables are loaded in chunks called "Pages" (typically 4096 
bytes, or 0x1000 in hex). 

Because the entire module is shifted as a single rigid block:
  • The distance (OFFSET) between any two functions inside the same module 
    is ALWAYS IDENTICAL.
  • The lowest 12 bits (the last 3 hexadecimal digits) never change!

Example observation:
  Run 1: leaked address = 0x7f83a124a560
  Run 2: leaked address = 0x7f55b8823560
  Run 3: leaked address = 0x7fc09d431560
  Notice: The prefix randomizes, but "...560" remains invariant!


[4. THE MATH OF ASLR DEFEAT]
--------------------------------------------------------------------------------
Every calculation in an ASLR bypass boils down to simple arithmetic:

                Runtime Leaked Address
                          -
                Known Static Offset of Leaked Function
             --------------------------------------------
                     = RUNTIME BASE ADDRESS

Once you have the Runtime Base Address:
  Target Address = Runtime Base Address + Known Static Offset of Target Function


[5. PRACTICAL WORKFLOW]
--------------------------------------------------------------------------------
1. Find the static offset using `readelf` or `nm`:
   $ readelf -s binary_or_libc | grep leaked_symbol
   Example: 0x000000000005a560

2. Connect with pwntools and receive the leak:
   from pwn import *

   p = process('./chall')
   p.recvuntil(b"interesting: ")
   leak_str = p.recvline().strip()
   leak_addr = int(leak_str, 16)
   log.info(f"Leaked Address: {hex(leak_addr)}")

3. Compute base and target:
   known_offset = 0x5a560
   base_addr = leak_addr - known_offset
   log.success(f"Calculated Base Address: {hex(base_addr)}")

   target_offset = 0x4f320
   target_addr = base_addr + target_offset
   log.info(f"Target Function is at: {hex(target_addr)}")


[6. CONCEPTS LEARNED]
--------------------------------------------------------------------------------
• ASLR (Address Space Layout Randomization): Defense mechanism against hardcoded exploits.
• Page Alignment (0x1000)                 : Why the lower 3 nibbles remain invariant.
• Relative Offsets                        : Constant distances between symbols in memory.
• Dynamic Address Calculation             : Computing runtime targets on the fly.
• Information Disclosure Vulnerability    : Why memory leaks are fatal to modern protections.


[7. PROGRESSIVE HINTS]
--------------------------------------------------------------------------------
Hint 1: Run the program 5 times in a row and compare the printed address. What parts 
        change, and what parts stay the same?

Hint 2: Look at the last 3 hexadecimal characters of the address across runs. Why do 
        they stay identical? What does that tell you about page boundaries?

Hint 3: If you know the offset of the leaked symbol from the module's base (via 
        `nm` or GDB `info address`), subtract that offset from your leak. You now 
        hold the randomized base address!
